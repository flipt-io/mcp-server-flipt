## Project Overview

A Model Context Protocol (MCP) server for [Flipt](https://flipt.io) feature flags, published to npm as `@flipt-io/mcp-server-flipt`. It exposes Flipt's REST API (namespaces, flags, segments, rules, rollouts, constraints, variants, distributions, evaluation) as MCP tools and prompts over STDIO transport.

## Commands

```bash
npm run dev        # Run from source with tsx (src/index.ts)
npm run build      # Compile TypeScript to dist/ (postbuild chmods dist + bin/cli.js)
npm start          # Run compiled server via bin/cli.js (requires build first)
npm run check      # Typecheck only (tsc --noEmit)
npm run lint       # ESLint on src/**/*.ts, excludes src/generated/
npm run lint:fix
npm run fmt        # Prettier write
npm run fmt:check
npm test           # Jest (ts-jest); tests live in src/tests/ (testMatch **/tests/**/*.test.ts)
```

To run a single test (once tests exist): `npx jest path/to/tests/foo.test.ts` or `npx jest -t "test name"`.

Runtime configuration comes from env vars (or a `.env` file, loaded via dotenv): `FLIPT_URL` (default `http://localhost:8080`) and optional `FLIPT_API_KEY` (sent as a Bearer token).

## Architecture

Three layers, all registration in one file:

- **`src/index.ts`** — the entire MCP surface. Every tool and prompt is registered inline here via `server.tool(name, zodSchema, handler)` / `server.prompt(...)` against a single `McpServer` from `@modelcontextprotocol/sdk`. Handlers call `FliptClient`, return results as JSON text content, catch errors and return `isError: true` responses. Resource-style URIs (`flipt://namespaces/...`) are attached in `_meta`. `startServer()` wires the STDIO transport; `bin/cli.js` is the published entrypoint that requires `dist/index.js`.
- **`src/services/fliptClient.ts`** — `FliptClient` wraps the generated OpenAPI client. It instantiates one `*ServiceApi` per Flipt resource type from a shared configuration (base URL + optional bearer auth). This is the only file that touches the generated code directly; some client methods exist but have no corresponding MCP tool yet (e.g., `updateRule`, `orderRules`, `updateConstraint`, `updateVariant`, `updateDistribution`, `listRollouts`).
- **`src/generated/api/`** — TypeScript fetch client generated by openapi-generator (config in `openapitools.json`, generator v7.12.0) from Flipt's OpenAPI spec. **Never hand-edit**; it is excluded from lint, tests, and coverage. Quirk to know: `RolloutList` exposes rollouts under a `rules` property.

`src/tests/` is excluded from the tsc build (so tests never land in `dist/`) and from ESLint's type-aware parsing; ts-jest type-checks tests independently.

## Adding a new MCP tool

1. Add/verify the API method on `FliptClient` (delegating to the appropriate generated `*ServiceApi`).
2. Register the tool in `src/index.ts` with a zod schema, following the existing pattern: try/catch, JSON.stringify result, `isError: true` on failure, `_meta.uri` for resource-addressable entities.

Update tools follow a read-merge-write pattern: fetch the current entity, merge changed fields, then call the update API (Flipt updates are full replacements, not patches). Merge optional fields with `??`, never `||` — `||` silently drops valid falsy values like `enabled: false`.

## Other notes

- `src/version.ts` holds the version reported to MCP clients. It is regenerated from `package.json` by `scripts/sync-version.js`, which runs automatically on `npm version <bump>`; a test in `src/tests/version.test.ts` fails if they drift.
- Publishing is via `.github/workflows/publish.yml` (npm) and Dockerfile (ghcr.io). `smithery.yaml` defines the Smithery install config and maps `fliptApiUrl`/`fliptApiKey` config onto the `FLIPT_URL`/`FLIPT_API_KEY` env vars — keep it in sync if env var names change (see commit b8079f6 for a past mismatch).
